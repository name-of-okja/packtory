# packtory 물류 흐름 모니터 설계

작성일: 2026-09-19
상태: 초안 (검토 대기)

## 1. 목적

신입 시설 관리·유지보수 담당자가 화면을 처음 봐도 **지금 라인이 도는지,
안 돌면 어디가 막혔는지**를 한 눈에 알 수 있게 한다.

평면도 위에 물류가 흐르는 모습을 애니메이션으로 그리고, 막힌 구간을
빨갛게 띄우고, 그 구간을 클릭하면 해당 구역 CCTV를 모달로 보여준다.

화면은 **어디서 멈췄는지**까지 답한다. **왜 멈췄는지**는 사람이 CCTV를
보고 판단한다. 그것이 이 제품에 CCTV가 있는 이유다.

## 2. 기존 스펙과의 관계

이 문서는 `2026-09-12-packtory-mvp-design.md` (v1) 를 **대체한다.**

뒤집힌 결정:

| v1 | 이 스펙 | 이유 |
|---|---|---|
| Babylon.js 3D 씬 | 2D 평면도 (SVG) + 층 탭 | 궤도 카메라는 탐색용이지 파악용이 아니다. 각도를 맞춰야 보이는 화면은 신입이 제일 못 하는 일이다 |
| 우측 상시 패널 | 모달 | 볼 곳이 둘로 나뉘면 "한 눈에"가 깨진다 |
| 장비가 카메라를 소유 | 섹션이 카메라를 소유 | 카메라 하나가 여러 장비를 비추는 현실. 섹션은 "어디서 멈췄는지"의 답이기도 하다 |
| 장비 중심 | 구간(흐름) 중심 | 멈추는 것은 장비가 아니라 물류다 |

유지된 결정: 어댑터 인터페이스, 와이어 프로토콜(`snapshot`/`values`,
`{tag,v,ts,q}`), 영상은 허브를 통과하지 않는다는 원칙, go2rtc 배치,
읽기 전용, 모의 데이터, H.264 전용, 씬 JSON 직접 편집.

## 3. 확정된 전제

| 항목 | 결정 | 근거 |
|---|---|---|
| 렌더링 | SVG 2D 평면도 | 클릭 히트테스트·텍스트 라벨·상태색이 전부 공짜. 에셋 파이프라인 없음. 점이 수백 개를 넘으면 그때 Canvas로 내린다 |
| Z축 | 층 선택 탭 | 네이버지도 실내지도 모델. 한 번에 한 층만 그리니 가림이 0 |
| 센서 신호 | 누적 카운터 | 100ms 폴링으로 ON/OFF만 받으면 빠른 제품을 통째로 놓친다. 카운터는 차분으로 알 수 있다 |
| 정지 판정 | 서버 (허브) | 방금 접속한 브라우저는 과거 이력이 없어 정지 시간을 계산할 수 없다 |
| 애니메이션 | 클라이언트 (CSS) | 점의 픽셀 위치는 아무도 안 따진다. 장식은 클라이언트 몫 |
| 데이터 소스 | 모의 생성기 | 실제 프로토콜 연결은 계약 후. 어댑터 인터페이스는 실제와 동일 |
| 제어 | 읽기 전용 | 쓰기는 안전·권한·감사로그를 동반하는 별도 제품 |

### 판정은 서버, 그림은 클라이언트

이 분리가 설계의 중심이다.

**정지 판정은 사실이다.** 모든 화면에서 같아야 하고 이력이 필요하다.
스냅샷은 현재 카운터 값만 주지 과거를 주지 않으므로, 10초 전에 연 화면은
`out` 이 3분째 안 움직였다는 것을 알 방법이 없다. 클라이언트가 계산하면
아침에 출근한 사람은 "정지 0초"부터 보게 된다 — 제품이 틀린 말을 한다.

**점의 위치는 장식이다.** 몇 픽셀에 있는지는 아무도 안 따지고, 서버가
초당 수백 개 좌표를 접속자 수만큼 밀면 서버가 상태 덩어리가 된다.

그래서 허브가 `wip`/`state`/`stallMs` 를 파생 태그로 계산해 밀고,
클라이언트는 그 숫자로 점만 흘린다. 허브가 구간당 들고 있는 상태는
`{ lastIn, lastOut, lastOutChangeTs }` 세 개뿐이다.

## 4. 아키텍처

```
외부 시스템            중개서버 (packtory-hub)          클라이언트
──────────            ───────────────────────          ──────────
OPC-UA   ─┐                                           ┌─ 웹 (React + SVG)
MQTT     ─┼→ 어댑터 → 정규화 → 파생 → WS 팬아웃 ──────┼─
REST     ─┤                     (판정)                 └─
모의생성기─┘

CCTV ─────→ go2rtc ────────────── WebRTC ──────────────→ 브라우저 직결
```

**비디오는 중개서버를 통과하지 않는다.** 게이트웨이에서 브라우저로 직접
간다. 서버가 영상 바이트를 중계하면 CPU와 대역폭이 카메라 수만큼 곱해진다.
중개서버는 카메라 스트림의 주소만 알려준다.

중개서버와 go2rtc는 같은 장비에 함께 배치한다. 둘 다 OT망에서
카메라·PLC에 닿아야 하고, 클라이언트는 사무망에서 접속한다.

## 5. 씬 모델 (스키마 v2)

전체 시스템이 이 파일 하나에 매달린다. 좌표 단위는 미터, 평면도 기준으로
X는 오른쪽, Y는 위쪽이다.

```json
{
  "version": 2,
  "name": "데모 라인",
  "stallSec": 10,

  "floors": [
    { "id": "1F", "label": "1층", "order": 1 },
    { "id": "2F", "label": "2층", "order": 2 }
  ],

  "sections": [
    { "id": "inbound", "label": "입고부", "floor": "1F",
      "rect": [0, 0, 40, 25], "cameras": ["cam-in-1"] },
    { "id": "filling", "label": "충전부", "floor": "2F",
      "rect": [0, 0, 24, 25], "cameras": ["cam-fill-1", "cam-fill-2"] },
    { "id": "packing", "label": "포장부", "floor": "2F",
      "rect": [24, 0, 16, 25], "cameras": [] }
  ],

      "from": { "floor": "2F", "x": 8,    "y": 12 },
      "to":   { "floor": "2F", "x": 16.5, "y": 12 },
      "capacity": 12, "wipOffset": 0 },

    { "id": "conv-5", "label": "포장 이송", "section": "packing",
      "from": { "floor": "2F", "x": 19.5, "y": 12 },
      "to":   { "floor": "2F", "x": 28,   "y": 12 },
```

### 필드

**floors** — `order` 는 탭의 표시 순서(큰 값이 위).

**sections** — `rect` 는 `[x, y, w, h]`. 배경을 칠하고 라벨을 놓는 용도일
뿐, 소속 판정에 쓰지 않는다. `cameras` 가 빈 배열이면 모달에 영상 자리가
없다.

**equipment** — `pos` 는 중심점, `size` 는 `[w, h]`. `tags` 의 `warn` 은
선택 필드이며, 있으면 임계, 없으면 경고 판정에서 제외한다.

**segments** — `from`/`to` 는 각각 `{ floor, x, y }`. `via` 는 선택이며
중간 경유점 배열이다. `capacity` 는 선택이며 표시용 최대치다.
`wipOffset` 은 선택(기본 0), `counterMax` 는 선택이다 (아래 7장 참조).

**리프트에 별도 타입을 두지 않는다.** `from.floor !== to.floor` 이면
리프트다. 그래서 리프트도 컨베이어와 똑같이 `in`/`out` 카운터를 갖고,
똑같은 정지 판정을 받고, 똑같은 코드로 다뤄진다 — 층간 마커로 그려진다는
것만 다르다. **물류가 제일 잘 막히는 지점을 특수 케이스로 만들지 않는
것**이 이 표현의 목적이다.

### 태그 이름 규칙

전역 태그 식별자는 `{id}.{key}` 다. 씬에 태그 이름 필드를 두지 않는다.

| 태그 | 출처 | 형 |
|---|---|---|
| `{equipment.id}.{tag.key}` | 어댑터 (원시) | number \| string \| boolean |
| `{segment.id}.in` | 어댑터 (원시) | number, 단조 증가 |
| `{segment.id}.out` | 어댑터 (원시) | number, 단조 증가 |
| `{segment.id}.wip` | 허브 (파생) | number |
| `{segment.id}.state` | 허브 (파생) | `"running"` \| `"stalled"` \| `"idle"` \| `"unknown"` |
| `{segment.id}.stallMs` | 허브 (파생) | number |

실제 PLC 주소와의 대응은 어댑터 설정의 몫이지 씬의 몫이 아니다.

`camera.stream` 은 `go2rtc.yaml` 의 스트림 이름과 **문자 그대로 같다.**
별도 매핑 테이블을 두지 않는다.

### 씬 검증

손으로 고치는 JSON이 시스템의 축이면 검증은 선택이 아니다. 허브가 부팅 시
씬을 읽고 아래를 검사한다. 하나라도 걸리면 **에러로 죽는다** (경고 항목
제외).

1. 참조 무결성 — `section.floor`, `equipment.section`, `segment.section`,
   `segment.from.floor`, `segment.to.floor`, `section.cameras[]` 가 모두
   존재하는 id를 가리킬 것
2. id 중복 없음 — floors/sections/cameras는 각 집합 내에서, **equipment와
   segments는 서로 간에도** 중복 불가 (태그 네임스페이스를 공유하므로
   같은 이름이면 태그가 충돌한다)
3. 장비의 `pos ± size/2` 가 소속 섹션의 `rect` 안에 있을 것
4. 같은 층의 섹션 `rect` 끼리 겹치지 않을 것
5. `segment.from` 과 `segment.to` 가 같은 좌표가 아닐 것
6. **경고** — 어느 섹션에서도 참조하지 않는 카메라

**구간 좌표는 섹션 rect를 벗어나도 된다.** 구간은 폴리라인이라 섹션
경계를 넘나드는 것이 정상이고 (위 예의 `conv-5`), `section` 필드는 기하가
아니라 관리 주체를 뜻한다. 그래서 소속을 rect로 자동 계산하지 않고 명시
필드로 둔다.

## 6. 와이어 프로토콜

v1에서 **한 글자도 바뀌지 않는다.** 파생 태그는 원시 태그와 같은 메시지에
그냥 섞여 온다.

### HTTP

`GET /api/scene`

```json
{
  "scene": { "...5장의 씬 문서..." },
  "go2rtcBase": "http://192.168.0.10:1984"
}
```

클라이언트는 `go2rtcBase` 와 `camera.stream` 을 조합해 영상 주소를 만든다.
엔드포인트는 이것 하나뿐이다.

### WebSocket

`GET /ws` 로 업그레이드. 클라이언트는 아무것도 보내지 않는다 (읽기 전용).

접속 직후 스냅샷 1회:

```json
{ "type": "snapshot", "data": [
  { "tag": "conv-3.in",      "v": 1420,      "ts": 1758240000000, "q": "good" },
  { "tag": "conv-3.out",     "v": 1385,      "ts": 1758240000000, "q": "good" },
  { "tag": "conv-3.wip",     "v": 35,        "ts": 1758240000000, "q": "good" },
  { "tag": "conv-3.state",   "v": "stalled", "ts": 1758240000000, "q": "good" },
  { "tag": "conv-3.stallMs", "v": 192000,    "ts": 1758240000000, "q": "good" }
]}
```

이후 변경분만 푸시 (100ms 간격으로 배치):

```json
{ "type": "values", "data": [
  { "tag": "conv-3.stallMs", "v": 192500, "ts": 1758240000500, "q": "good" }
]}
```

- `v`: number | string | boolean
- `ts`: epoch 밀리초
- `q`: `"good" | "bad"`. 소스 연결이 끊긴 태그는 `"bad"`

**클라이언트는 파생과 원시를 구분하지 않는다.** 씬이 `conv-3` 은 구간이라고
알려줬으니 `conv-3.state` 를 찾아야 한다는 것을 이미 안다. 파생 표시가
필요 없다.

재접속: 연결이 끊기면 클라이언트가 3초 간격으로 재시도하고, 재접속에
성공하면 서버가 스냅샷을 다시 보낸다. 클라이언트는 스냅샷을 받을 때마다
로컬 값 상태를 통째로 교체한다.

## 7. 허브 (packtory-hub)

Node 20 + TypeScript. `node:http` + `ws` 패키지. 엔드포인트가 2개뿐이라
웹 프레임워크를 쓰지 않는다.

```
hub/
  scene.ts        씬 로드 + 검증 (5장)
  adapter.ts      인터페이스 (v1 그대로)
  adapters/mock.ts
  derive.ts       ← 새로 생기는 유일한 로직
  cache.ts        마지막 값 (스냅샷용)
  ws.ts           팬아웃
  index.ts        조립 + HTTP
```

### 어댑터 인터페이스 (v1 그대로)

```ts
interface Adapter {
  start(emit: (tag: string, v: Value, ts: number, q?: Quality) => void): Promise<void>
  stop(): Promise<void>
}
```

확장 시 `OpcUaAdapter`, `MqttAdapter` 가 같은 인터페이스를 구현하며,
클라이언트는 아무것도 바뀌지 않는다.

### derive.ts

이 서버의 로직은 전부 여기 있다. 테스트 가능하도록 순수 함수로 둔다:

```ts
type SegMemory = {
  lastIn: number
  lastOut: number
  lastOutChangeTs: number
}

derive(segments, values, prev, now, stallSec) -> { tags: Value[], next: Map<string, SegMemory> }
```

구간마다:

```
in, out 중 하나라도 q === "bad" 또는 값이 없음
  → state = unknown, wip = 0, stallMs = 0, 전부 q = "bad"

델타 계산:
  counterMax 있으면  d = (v - last + counterMax + 1) % (counterMax + 1)
  counterMax 없고 v < last  → PLC 재기동으로 간주:
      재기준선(lastIn = in, lastOut = out, lastOutChangeTs = now)
      이번 주기는 state = unknown

out이 증가했으면 lastOutChangeTs = now

wip = max(0, in - out + wipOffset)

now - lastOutChangeTs < stallSec * 1000  → running,  stallMs = 0
wip > 0                                   → stalled,  stallMs = now - lastOutChangeTs
그 외                                     → idle,     stallMs = 0
```

**500ms 타이머로 돈다.** 값이 안 바뀌어도 돌아야 `stallMs` 가 올라간다 —
정지 시간은 아무 일도 안 일어날 때 세는 숫자다. 원시 값은 어댑터가 내보낼
때마다, 파생 값은 500ms마다 캐시에 들어가고, 팬아웃은 둘을 합쳐 100ms마다
배치로 내보낸다.

### 현장에서 반드시 만나는 세 가지

**카운터 랩어라운드.** 16비트 PLC 카운터는 초당 10개면 두 시간이 안 돼 한
바퀴 돈다. `in - out` 이 음수로 튀면 WIP가 쓰레기가 되고 화면은 조용히
거짓말을 시작한다. 씬의 `counterMax` 가 있으면 모듈러로 델타를 구하고,
없으면 음수 델타를 PLC 재기동으로 간주해 재기준선을 잡고 그 구간을 한 주기
`unknown` 으로 내린다.

**WIP 영점.** `in - out` 은 두 카운터가 같이 0에서 출발했을 때만 맞는다.
일주일 돌던 라인에 붙으면 영점이 어긋나 있다. `wipOffset` 이 보정
손잡이다 — 구간을 비운 상태에서 한 번 `-(in - out)` 을 넣으면 맞는다.
실물이 붙는 시스템에 보정 손잡이가 없으면 숫자가 안 맞고, 안 맞으면
아무도 안 본다.

**허브 재기동.** `lastOutChangeTs` 가 날아가 모든 구간이 `stallSec` 동안
`running` 으로 보인다. 디스크에 남기지 않는다 — 최대 오차가 기본 10초이고
스스로 복구되는 것을 위해 DB를 들이는 것은 손해다.

### 모의 어댑터

구간마다 목표 속도로 `in`/`out` 카운터를 100ms 주기로 증가시키고, 장비
태그는 사인파 + 노이즈로 만든다. 데모용으로 특정 구간의 `out` 만 주기적으로
멈춘다.

**판정 로직을 흉내내지 않고 원인만 만든다.** `out` 을 멈추면 WIP가
차오르면서 진짜 `derive.ts` 가 `stalled` 를 판정한다. 모의 어댑터가
`state` 를 직접 쓰면 판정 코드는 데모에서 한 번도 실행되지 않는다.

### 테스트

`derive.ts` 하나에만 붙인다 — running/stalled/idle/unknown 전이,
카운터 리셋, 랩어라운드, `wipOffset`, 정지시간 누적. 나머지는 배선이라
테스트할 것이 없다.

### 하지 않는 것

히스토리 저장, 알람 엔진, 인증, 멀티 씬, 값 쓰기. 캐시는 마지막 값만
메모리에 들고 있는다.

## 8. 클라이언트

Vite + React + TypeScript. 3D 라이브러리 없음.

```
web/src/
  scene.ts       타입 + GET /api/scene
  useValues.ts   WS 훅 (3초 재접속, 스냅샷 시 전체 교체)
  Map.tsx        SVG 지도 — viewBox 팬/줌
  Segment.tsx    구간 선 + 점 + 리프트 마커
  FloorTabs.tsx  층 탭 + 상태 배지
  AlertBar.tsx   상단 이상 칩
  Modal.tsx      CCTV + 수치
  App.tsx
```

### 화면

```
┌──────────────────────────────────────────────────────────┐
│ ⚠ 충전부 conv-3 정지 3:12   ⚠ 입고부 lift-1 정지 0:48     │ ← 이상 칩
├────┬─────────────────────────────────────────────────────┤
│ 2F │   ┌─ 충전부 ──────────────┐┌─ 포장부 ────────┐      │
│ 🔴 │   │ ▣충전기1 ━●●●●●━╳ ▣캡퍼││  ━●━▶  ▣포장기1 │      │
├────┤   │    ⚠78°C        📹×2  ││                 │      │
│ 1F │   └───────────────────────┘└─────────────────┘      │
│ 🟢 │        ▲1F ← lift-1                                  │
└────┘                                        [⌂] [+] [-]  │
└──────────────────────────────────────────────────────────┘
```

**상시 패널은 두지 않는다.** 지도가 화면을 다 쓴다. 값은 호버 툴팁,
상세는 모달로 간다. 볼 곳이 두 군데로 나뉘면 "한 눈에"가 깨진다.

**상단 이상 칩이 이 제품의 핵심이다.** `state === "stalled"` 인 구간만
칩으로 뜬다. 칩을 누르면 해당 층으로 전환되고 지도가 그 구간으로 팬한다.
**신입이 찾을 필요가 없다 — 화면이 데려다준다.** 전부 정상이면 칩 자리에
"정상 가동"만 뜬다.

지도는 SVG `viewBox` 하나로 팬/줌한다. 섹션 라벨은 항상, 장비·구간 라벨은
일정 배율 이상에서만 뜬다. `⌂` 버튼이 현재 층 전체보기로 되돌린다.

층을 전환하면 다른 층의 DOM은 언마운트한다.

### 상태 표현

| 상태 | 표현 | 뜻 |
|---|---|---|
| running | 초록 실선, 점이 흐름 | 돌고 있음 |
| **stalled** | **빨강 점선 깜빡임, 점이 얼어붙음** | **막힘. 사람이 가야 함** |
| idle | 회색 실선, 점 없음 | 물건이 안 들어옴. 정상 |
| unknown | 빗금, 점 없음 | 센서/통신 끊김 |

**정지와 대기를 가르는 것이 제품의 값어치다.** 둘 다 "안 돌고 있음"이지만
빈 컨베이어가 멈춘 것은 정상이고 꽉 찬 컨베이어가 멈춘 것은 사고다. 이것을
구분하지 못하면 신입이 하루에 열 번 헛걸음하고, 그러면 화면을 안 본다.
빨강은 오직 `wip > 0` 일 때만 쓴다.

색만으로 구분하지 않는다 — 정지는 점선 깜빡임, 불명은 빗금이 같이 붙는다.

**장비 경고는 다른 언어를 쓴다.** 구간 정지는 선이 빨강, 장비 경고
(`warn` 초과)는 박스에 주황 테두리. 모양도 색도 달라 겹쳐 봐도 헷갈리지
않는다. 장비 경고는 이력이 필요 없는 순간 판정이라 클라이언트가 계산한다.

### 애니메이션

**개별 아이템을 추적하지 않는다.** 화면에 필요한 정보는 두 개뿐이다 —
몇 개가 들어있나(`wip`), 움직이나(`state`).

```
점 개수  = min(wip, capacity)   구간이 꽉 차면 꽉 차 보인다
남는 개수 = "+92" 숫자
점 움직임 = state  running이면 재생, 그 외 정지
```

점을 `capacity` 에서 끊는 이유는 수학이다. 점 i 의 위상이
`(t/dur + i/capacity) mod 1` 이므로 i 와 i+capacity 는 **정확히 겹친다** —
`capacity` 를 넘겨 그리면 보이지 않는 원만 쌓인다. 끊어 놓으면 구간이 꽉 찰
때까지 점이 차오르고 그 위는 숫자가 말한다. `MAX_DOTS = 30` 은 그 위에 남는
안전 상한이다 (capacity 를 크게 적은 씬으로부터 브라우저를 지킨다).

그래서 애니메이션을 JS로 돌리지 않는다. CSS가 한다:

```css
.item {
  offset-path: path(var(--seg-path));
  animation: flow var(--seg-duration) linear infinite;
  animation-delay: calc(var(--i) / var(--n) * var(--seg-duration) * -1);
}
.segment[data-state="stalled"] .item { animation-play-state: paused; }
@keyframes flow { to { offset-distance: 100%; } }
```

`animation-delay` 음수값이 점들을 경로에 고르게 깔아준다. 브라우저가
컴포지터에서 돌리니 메인 스레드에 프레임 루프가 없다. React는 값이
갱신되는 주기로만 리렌더한다 — 60fps로 원 200개를 리렌더하는 일은
일어나지 않는다. 점은 인덱스로 key를 주어 WIP가 늘어도 기존 점의
애니메이션이 끊기지 않는다.

**속도는 경로 길이에 비례한 고정값이다.** 처리량에 비례시키지 않는다 —
눈으로 읽을 수 없는 차이인데 `animation-duration` 을 중간에 바꾸면 점이
튄다.

**적체는 저절로 보인다.** 막힌 구간은 `out` 이 멈춘 채 `in` 만 들어오니
WIP가 차오르고 점 개수가 그대로 늘어난다. 멈춘 데다 점이 빽빽한 구간과,
멈췄는데 텅 빈 구간이 눈으로 구분된다 — 사고와 정상의 차이가 글자 없이
읽힌다.

```
running  ━━●━━━●━━━●━━▶      점 3개, 흐름
stalled  ━●●●●●●●●●●●━╳      점 12개, 얼어붙음, 빨강 점선 깜빡임
idle     ━━━━━━━━━━━━━        점 없음, 회색
unknown  ╱╱╱╱╱╱╱╱╱╱╱╱         빗금
```

**리프트는 경로가 없으니 층 사이 마커로 그린다.** 각 층 지도의 해당
지점에 `▲2F` / `▼1F` 마커, 옆에 WIP 배지. 상태색은 구간과 동일하게
붙는다. 클릭하면 상대 층으로 전환한다.

**`prefers-reduced-motion` 을 존중한다.** 애니메이션을 끄고 점은 정적으로
깔린다 — 상태는 색·점선·개수가 이미 다 전달하므로 정보가 하나도 사라지지
않는다. CSS 미디어쿼리 한 줄이다.

### 모달

대상이 섹션이든 장비든 구간이든 **같은 모달이고 내용만 다르다.**
CCTV는 언제나 그 대상이 속한 섹션에서 온다.

| 대상 | 내용 |
|---|---|
| 섹션 | 섹션 CCTV + 그 섹션 구간들의 상태 목록 |
| 장비 | 태그 값 목록 + 소속 섹션 CCTV |
| 구간 | `in`/`out`/`wip`/정지시간 + 소속 섹션 CCTV |

카메라가 여러 대면 탭이고 활성 탭 하나만 재생한다. 카메라가 없는 섹션은
영상 자리 없이 수치만 뜬다.

**모달이 열려 있을 때만 스트림을 건다.** go2rtc의 `video-stream.js` 웹
컴포넌트를 그대로 쓰고, 모달을 닫으면 끊는다. 동시 디코딩 스트림은 항상
1개다. 영상은 `<video>` 로만 표시하고 지도에 입히지 않는다.

## 11. 완료 기준

이 각본이 끝까지 돌면 완료다.

1. 접속하면 현재 층 평면도에 섹션·장비·구간이 뜨고, 가동 중 구간에 점이 흐른다
2. 층 탭이 층 수만큼 뜨고 각각 상태 배지를 단다. 탭을 누르면 그 층 지도로 바뀐다
3. 모의 어댑터가 `conv-3.out` 을 멈추면 → `stallSec` 뒤 그 구간이 빨강 점선으로 바뀌고, 점이 얼어붙고, 점이 `capacity` 까지 차오른 뒤로는 `+N` 숫자가 계속 커진다
4. 동시에 상단에 `충전부 conv-3 정지 0:12` 칩이 뜨고 초가 올라간다
5. 다른 층을 보고 있어도 그 층 탭이 빨개진다
6. 칩을 클릭하면 해당 층으로 전환되고 지도가 그 구간으로 팬한다
7. 구간을 클릭하면 모달에 `in`/`out`/`wip`/정지시간과 그 섹션 CCTV 라이브가 뜬다 (지연 1초 미만)
8. **물건이 안 들어와서 멈춘 빈 구간은 회색 `idle` 로 남고 칩이 뜨지 않는다** — 데모에서는 `conv-5` 가 40~95초에 굶어 비워지므로, 50초쯤부터 90초까지 같은 2층 화면에 **빨갛게 꽉 찬 `conv-3` 과 회색으로 텅 빈 `conv-5` 가 나란히** 뜬다. 두 구간이 한 화면에 같이 보이는 것이 이 항목의 합격 신호다
9. **브라우저를 새로 열어도 정지 시간이 이어서 맞게 나온다** (0초부터 다시 세지 않는다)
10. 리프트를 클릭하면 상대 층으로 전환된다
11. 허브를 재시작하면 클라이언트가 자동 재접속하고 스냅샷으로 전체를 다시 받는다
12. 카메라 없는 섹션(`packing`)을 클릭하면 영상 자리 없이 수치만 뜬다

**8번과 9번이 이 설계의 시험지다.** 8번이 깨지면 빨강이 흔해져 아무도 안
보고, 9번이 깨지면 화면이 거짓말을 한다. 나머지 열 개가 다 돌아도 이 둘이
안 되면 제품이 아니다.

## 13. 확장 경로

순서대로. 각 단계는 앞 단계의 인터페이스를 바꾸지 않는다.

1. **실제 어댑터** — `OpcUaAdapter` 를 `Adapter` 인터페이스로 구현.
   허브와 클라이언트 무변경
2. **씬 에디터** — 지도 위에서 드래그 배치, 씬 JSON 저장. 2D라 좌표가
   2개뿐이라 v1의 3D 기즈모보다 훨씬 싸다
3. **정지 이력** — `stallMs` 를 시계열로 적재. 가동률 집계의 전제
4. **알람 통지** — 정지가 N분 넘으면 푸시/메일
5. **다중 카메라 타일** — 가시성 기반 재생 제어 정책 필요
6. **H.265** — go2rtc 트랜스코딩 설정. 카메라당 CPU 예산 산정 필요
