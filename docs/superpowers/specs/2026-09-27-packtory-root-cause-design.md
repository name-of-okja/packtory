# packtory 원인 추적 설계 (하위 프로젝트 B)

작성일: 2026-09-27
상태: 승인됨, 구현 중 실측으로 고침 (2026-09-27)

## 1. 목적

하위 프로젝트 A 로 대형 5층 네트워크가 돌기 시작하자, **막힘 하나가 평균
13개 안팎의 빨간 구간으로 번진다.** 막힌 곳의 상류가 차례로 꽉 차 멈추기
때문이다. 신입이 보는 화면에는 빨강이 열 개 넘게 뜨고, 그중 **가서 봐야 할
곳은 하나**다.

이 하위 프로젝트는 그 하나를 짚는다:

- **원인** — 하류에 빈자리가 있는데도 내보내지 못하는 구간. 빨강으로 남는다.
- **영향** — 하류가 전부 멈춰서 기다리는 구간. **노랑**으로 바꾼다.

성공의 모습: 막힘이 번진 화면에서 **빨강은 원인 하나, 나머지는 노랑**이고, 칩은
원인 하나만 "정지 1:24 · 영향 12" 로 선다. "빨강 = 가서 봐야 할 곳" 이 다시 참이 된다.

### 하위 프로젝트 A 와의 관계

A 가 남긴 것을 쓴다:

- `shared/graph.ts` 의 `downstream()`/`topoOrder()` — 연결의 출처만 끝점 추론에서
  `next` 필드로 바꾼다.
- 전파 mock — 막힘 각본을 알고 있으므로 **정답지**다. 판정이 맞는지를 mock 이
  막은 구간과 비교해 시험한다.

## 2. 확정된 전제

| 항목 | 결정 | 근거 |
|---|---|---|
| 화면 표현 | 원인만 빨강, 영향은 노랑 | 빨강이 다시 드물어져야 "빨강 = 가서 볼 곳" 이 된다 |
| 영향 색 | **노랑, 점멸 없음** | 주황은 이미 설비 경고 발광(`WARN_GLOW`)이다. 섞이면 "온도 경고" 와 "막힘 영향" 이 같은 색이 된다 |
| 연결의 출처 | `Segment.next?: string[]` **하나만** | 현장 씬은 손으로 그려 끝점이 정확히 안 맞는다(A 에서 작은 씬도 억지로 맞췄다). 출처가 둘이면 파일만 봐서는 어디로 이어졌는지 모른다 |
| 끝점 추론 | **지운다** | 위와 같다 |
| 판정 위치 | 서버. `derive` 뒤에 도는 순수 함수 `classify()` | 판정은 서버, 그림은 클라이언트 (기존 원칙). 모든 화면이 같은 답을 본다 |
| 스키마 | `version: 4`. v3 는 거절한다 | 씬이 하나뿐이다. 호환 코드를 둘 이유가 없다 |

## 4. 스키마 v4

```ts
export type Segment = {
  // … v3 필드 그대로 …
  /** 이 구간이 물건을 넘겨주는 구간들. 없거나 비었으면 출구(sink)다 */
  next?: string[]
}

export type Scene = { version: 4; /* … */ }
```

### 검증 규칙 (부팅 때, 기존 규칙에 더한다)

| 규칙 | 종류 | 내용 |
|---|---|---|
| 9 | 에러 | `next` 가 없는 구간 id 를 가리킨다 |
| 10 | 에러 | `next` 가 자기 자신을 가리킨다 |
| 11 | 에러 | 연결에 순환이 있다. **순환에 걸린 구간 id 를 나열한다** (A 에서 미룬 사소한 문제 — 대형 씬에서 손으로 끝점 하나를 고쳐 순환이 생기면 어디인지 찾을 수가 없었다) |
| 12 | 경고 | `next` 로 이어진 두 구간의 끝점(앞 구간의 `to`, 뒤 구간의 `from`)이 1m 넘게 떨어져 있거나 층이 다르다. 연결은 되지만 화면에서 선이 끊겨 보인다 |

`topoOrder()` 는 순환일 때 `null` 대신 **순환과 그 하류의 구간 id 들**을
알려줄 수 있어야 한다 (규칙 11 의 메시지). 반환형을
`{ order: string[] } | { cycle: string[] }` 로 바꾼다.

## 5. 연결을 `next` 에서 읽는다

- `downstream(scene)` 는 `seg.next ?? []` 를 그대로 돌려준다. 끝점 키 비교 코드는 지운다.
- 생성기는 구간을 다 만든 뒤, 끝점 일치로 `next` 를 **한 번 계산해 써 넣는다**
  (생성기 안에서만 쓰는 도우미). 생성기가 이어 그리므로 규칙 12 경고는 0 건이어야 한다.
- 작은 `scene.json` 은 손으로 쓴다: `conv-1 → lift-1 → conv-3 → conv-5`.
- `scene.large.json` 은 다시 생성해 커밋한다.

## 6. 원인·영향 판정 (`hub/src/cause.ts`)

```ts
export type Classified = { state: SegState; root: string }

/**
 * derive 가 낸 state 를 연결을 따라 다시 나눈다. stalled 만 바뀐다:
 * 하류가 전부 stalled·blocked 이거나 꽉 찼으면(WIP ≥ capacity × 0.8) blocked(영향), 아니면 stalled(원인).
 */
export function classify(
  down: Map<string, string[]>,
  order: string[],             // 위상 순서 (상류가 먼저)
  states: Map<string, SegState>,
  stallMs: Map<string, number>,
  full: Set<string>,           // 꽉 찬 구간 (WIP ≥ capacity × 0.8)
): Map<string, Classified>
```

### 규칙

위상 **역순**(하류부터)으로 한 번 훑는다.

| 구간의 derive state | 하류 | 결과 | `root` |
|---|---|---|---|
| stalled | 없음 (출구) | `stalled` (원인) | `""` |
| stalled | **전부** stalled/blocked/꽉 찬 running | `blocked` (영향) | 하류들의 원인 중 가장 오래 멈춘 것 (없으면 `""`) |
| stalled | 하나라도 running/idle/unknown | `stalled` (원인) | `""` |
| 그 외 | — | 그대로 | `""` |

- 하류의 원인은 하류가 원인이면 하류 자신, 영향이면 하류의 `root`, 꽉 찬 running 이면
  그 구간이 자기 하류에서 물려받은 원인이다.
- **꽉 찬 running 을 기다림으로 치는 이유 (실측으로 고침):** 막힘이 번진 망에서 합류점
  아래 구간은 꽉 찬 채 조금씩 움직여 running 이다. 그 자리를 다투다 몫을 못 받은
  상류가 원인으로 오판돼 막힘과 무관한 곳에 빨강이 계속 켜졌다. 기준을 딱 capacity 로
  하면 한 칸 빈 순간마다 깜빡여 80% 로 잡았다. 꽉 찬 running 아래에 원인이 없으면
  영향이되 `root` 는 비어 있다 — 원인 없는 정체다 (칩에 세지 않는다).
- 하류가 **unknown** 이면 기다리는 중이라고 증명할 수 없으므로 원인으로 둔다.
  센서가 끊긴 하류 때문에 멈춘 것처럼 보이는 구간을 노랑으로 숨기면 안 된다.
- 하류가 **idle**(비어서 쉼)인데 이 구간이 꽉 찬 채 멈췄다면, 고장은 그 사이에
  있다 — 원인이다.

### 알려진 한계 (스펙이 받아들인다)

한 줄에 원인이 둘이면(하류가 막혀 있는 동안 상류도 따로 고장 남) 상류 쪽은 영향으로
보인다. 하류가 막혀 있는 동안에는 상류가 따로 고장인지 카운터만으로 가를 수 없다.
하류가 풀리면 상류가 원인으로 바뀌어 드러난다.

### 허브 배선

`index.ts` 의 판정 타이머(500ms)에서 `derive` 다음에 `withCause`(안에서 `classify`)를 부른다. 구간별 `capacity` 를 넘긴다(꽉 참 판단).
`.state` 태그는 분류 결과로 낸다. 새 태그 `{id}.root` (문자열, 해당 없으면 `""`)
를 구간마다 낸다. 캐시가 바뀐 값만 밀기 때문에 대부분의 틱에서 `.root` 는
전송되지 않는다.

`down` 과 `order` 는 부팅 때 한 번 만든다 (씬은 바뀌지 않는다).

### 타입

`SegState` 에 `"blocked"` 를 더한다. `derive` 는 여전히 4가지만 낸다 — `blocked`
는 `classify` 만 만든다. `STATE_LABEL.blocked = "영향"`.

## 7. 화면

### 신호등

| 상태 | 램프 | 물건 |
|---|---|---|
| `stalled` (원인) | 빨강 점멸 (그대로) | 꽉 찬 채 멈춤 |
| `blocked` (영향) | **노랑, 점멸 없음** | 꽉 찬 채 멈춤 (흐름은 running 이 아니면 이미 멈춘다) |
| 나머지 | 그대로 | 그대로 |

멀리서 보기에 서는 램프: 원인·영향·불명 (`lampVisibleFar` 에 `blocked` 추가).
노랑 기둥이 막힘이 어디까지 번졌는지를 보여주고, 빨강은 그 끝에 하나 남는다.

### 라벨

- 멀리서: **원인 구간만** 이름과 정지 시간. 영향 구간은 램프만.
- 가까이서: 영향 구간에 노랑 정지 시간과 "C-92 때문에 대기" (원인 구간의 라벨).

### 구역 배지

| 구역 안에 | 배지 |
|---|---|
| 원인이 있다 | 빨강 "3층 B구역 · 정지 1 · 영향 4" (영향 0 이면 "· 정지 1") |
| 영향만 있다 | **노랑** "2층 A구역 · 영향 6" — 원인은 다른 구역에 있다 |
| 둘 다 없다 | 초록 "정상" (그대로) |

### AlertBar

- 칩은 **원인만**: "⚠ 1층 출고 C C-92 정지 1:24 · 영향 12". 영향 수 = `root` 가
  그 구간인 blocked 구간 수. 정렬은 그대로 정지 시간 긴 순.
- 5개 상한·"외 N건" 유지. 원인만 세므로 대개 한두 개다.
- 스크린리더 알림: "정지 1건: C-92 (영향 12)".

### 모달

- 영향 구간: 상태 "영향", 정지 시간 표시, **"원인: C-92 충전 이송 →" 버튼**. 누르면
  모달을 닫고 원인 구간으로 날아간다 (기존 `goTo`).
- 구역 모달의 구간 목록에서도 영향은 "영향 1:05" 로 읽힌다.

## 8. 테스트

### 자동 (hub, `node --test`)

| 대상 | 확인 |
|---|---|
| 검증 규칙 9~12 | 각 규칙이 걸리는 최소 씬, 규칙 11 메시지에 순환 구간 id 들 |
| `topoOrder` | 순환이면 `{ cycle }` 에 순환에 걸린 id 가 들어 있다 |
| `downstream` | `next` 그대로, 없으면 `[]` |
| 생성기 | 모든 `next` 가 실재 id, 규칙 12 경고 0, 기존 불변식 전부 |
| `classify` | 체인(끝만 원인), 합류(두 상류 영향, root 같음), 분기 한쪽만 막힘(상류는 running 이라 대상 아님), 출구 정지(원인), 하류 idle(원인), 하류 unknown(원인), 원인 둘 중 오래 멈춘 쪽이 root |
| **mock 정답 대조** | 전파 mock + `derive` + `classify` 를 대형 씬에서 20분 돌린다. 매 판정마다 둘을 확인한다. ① 지금 막힌 구간이 stalled 면 원인이다(다른 막힘의 상류면 예외 — 알려진 한계). ② 원인은 **지금 막힌 구간이거나, 풀린 지 `stallSec` 이내인 막힘의 상류**뿐이다. **오판은 원인 판정의 0.5% 이하, 같은 구간이 두 번 잇달아 틀리지 않는다** — 카운터만으로 못 가르는 순간이 드물게 있다(시드 8개 × 20분에서 원인 판정 약 4000번 중 0~4번, 전부 0.5초짜리, 실측) |
| 화면 요약 함수 | `affectedCounts`, `sectionSummary`, `badgeText` 의 각 경우 |

mock 정답 대조를 위해 mock 이 **지금 막고 있는 구간 목록**을 테스트에 알려줄 수
있어야 한다: `MockAdapter.blockedNow(): string[]` (테스트·디버그용, 판정에는 안 쓴다).

### 사람 (`docs/BROWSER-CHECKLIST.md` v5)

1. 막힘이 번지면 빨강 하나, 나머지는 노랑 (점멸 없음).
2. 칩은 원인 하나 "· 영향 N".
3. 멀리서: 노랑 기둥이 번진 범위를 보여주고, 라벨은 원인만.
4. 영향만 있는 구역 배지가 노랑.
5. 영향 구간을 눌러 모달 → "원인: … →" → 원인 구간으로 날아간다.
6. 설비 경고 발광(주황)과 영향(노랑)이 한 화면에서 구별된다.
7. 막힘이 풀리면 노랑·빨강이 함께 초록으로 돌아온다 (노랑이 남지 않는다).
